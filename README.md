# User Management API

An ASP.NET Core Web API for TechHive Solutions' internal HR and IT tools. It provides CRUD operations for user records and keeps data in memory for this activity.

## Requirements

- .NET 10 SDK

## Run the API

From this project directory, run `dotnet run`. The HTTP profile listens at `http://localhost:5093`. The API redirects HTTP requests to HTTPS when started with the HTTPS profile; use the URLs printed by `dotnet run` if the selected profile differs.

The API requires a Bearer token for all endpoints, including the Development OpenAPI document at `/openapi/v1.json`. In Development, use the sample token `dev-only-change-me` (set in `appsettings.Development.json`). This is a local demonstration token only; replace it with a secure value and do not use it outside a development environment. Outside Development, supply `Authentication__BearerToken` through a secure environment or secret provider. The API refuses to start outside Development if that setting is missing. This simple shared-token demonstration is not a substitute for an identity provider and signed, expiring JWTs in a production system.

## Middleware and authentication

The configured pipeline is ordered as follows:

1. `ExceptionHandlingMiddleware` catches unhandled downstream exceptions, logs details on the server, and returns a generic `500` JSON body: `{"error":"Internal server error."}`. Exception details are not sent to clients. Status-code pages retain Problem Details for otherwise body-less HTTP errors such as `404`.
2. ASP.NET Core authentication validates the `Authorization: Bearer <token>` header using a constant-time comparison. Authorization applies a fallback policy requiring an authenticated principal, so routes are protected by default. Missing or invalid credentials receive `401` with a JSON error.
3. `RequestResponseLoggingMiddleware` logs method, path, response status, and elapsed time. It wraps HTTPS redirection, authorization, and endpoint execution so rejected and redirected requests are logged too. It never logs the bearer token or request body.

In Development only, `GET /_debug/throw` intentionally throws to verify the exception middleware. Call it with the development Bearer token; expect `500` and the generic JSON error body. This route is not mapped outside Development.

## Endpoints

| Method | Route | Success response |
| --- | --- | --- |
| GET | `/api/users` | `200 OK` with a user array |
| GET | `/api/users/{id}` | `200 OK` with one user; `404 Not Found` if absent |
| POST | `/api/users` | `201 Created` with the new user and a `Location` header |
| PUT | `/api/users/{id}` | `200 OK` with the updated user; `404 Not Found` if absent |
| DELETE | `/api/users/{id}` | `204 No Content`; `404 Not Found` if absent |

POST and PUT accept `firstName`, `lastName`, `email`, and optional `department` JSON properties. Names and email are required, email must be valid, and field lengths are bounded. Invalid requests receive `400 Bad Request`; an email already assigned to another user receives `409 Conflict` (email matching is case-insensitive). IDs are generated by the API. Creation and update timestamps are returned in UTC.

## Exercise the API

Open `UserManagementAPI.http` in VS Code with the REST Client extension or use Postman. It contains requests for listing, creating, retrieving, updating, duplicate-email handling, and deleting a user. Run the create request first; the remaining requests use its response ID. The API starts with an empty list. Because storage is in memory, records are cleared when the process stops.

The request collection includes no-token and invalid-token checks (both should return `401`) and a Development-only exception test (should return `500`). It uses the Development sample token in its `@bearerToken` variable; update that variable to match the configured token when testing with another value.

Middleware smoke checks confirmed missing and invalid tokens return `401` JSON with a Bearer challenge, the configured token can access protected routes, and the Development test route returns exactly `{"error":"Internal server error."}` with status `500`. Console output included method/path/status/duration records for successful, unauthorized, and failed requests, without logging credentials. Production startup was also checked to fail when no token is configured.

### Verification performed

The endpoints were smoke-tested against the running API: create returned `201` with a `Location` header, list and retrieve returned `200`, malformed input returned `400`, a case-insensitive duplicate email returned `409`, update returned `200`, delete returned `204`, and retrieving deleted or unknown users returned `404` Problem Details. The OpenAPI document was also checked. `dotnet build` completed with zero warnings and errors, and workspace diagnostics reported no errors. No automated test project has been added in this phase.

## Debugging activity: bugs found and fixes

- **Unexpected exceptions had no consistent API response:** added explicit exception handling that logs failures server-side and returns a generic JSON `500` without exposing exception details. Status-code pages retain Problem Details for body-less HTTP errors. The API does not add broad per-action `try/catch` blocks that could hide failures.
- **Missing-user and duplicate-email error bodies were inconsistent or empty:** preserved the existing `404` behavior and changed duplicate-email responses to RFC 7807 Problem Details. Status-code pages also provide Problem Details for otherwise body-less error responses.
- **Listing users sorted the complete collection on every request:** removed the unnecessary ordering step. The list endpoint now returns a snapshot in $O(n)$ time instead of sorting in $O(n \log n)$; no ordering guarantee is part of the API contract.
- **Validation needed edge-case verification:** the existing data annotations reject blank names, malformed emails, and oversized fields, and `[ApiController]` returns `400` validation details automatically. Added invalid-payload and unknown-ID examples to the HTTP request file and re-tested these cases.

## Limitations

This activity version uses process-local memory rather than a database. Data is not persistent across restarts and is not shared between multiple API instances. A later phase can replace `UserStore` with persistent storage.
